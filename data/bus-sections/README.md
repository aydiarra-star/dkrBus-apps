# Portions de bus affichables, sans service daté

Dans *Trajet*, les **43 repères** du groupe « Portions de bus cartographiées » délimitent **35 attributions de portions à une fiche et à un sens** (plusieurs décrivent la même rue). La question est : *par quelle rue la ligne est-elle documentée entre ces repères ?* Sélectionner un de ces **repères de carte** ne permet pas de monter dans le calcul daté. Sur la DDD 1, huit quais vers Leclerc et deux vers les Parcelles ont des identités distinctes : [Médina et preuve par sens](../../docs/validation-physique.md). Le [poteau 18/39 rue GT-54](gt54-pins.json) est un contrôle hors graphe, pas une sélection de montée. Pour les accès piétons effectivement calculables sur B1, voir la [revue des quais de Scat Urbam et Petersen](acces-scat-urbam.md).

**Données et droits.** Géométrie, identifiants, membres et sens de voirie : [© les contributeurs OpenStreetMap](https://www.openstreetmap.org/copyright), [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/). L’extrait réutilisable est dans [`busSectionWays.ts`](../../src/data/busSectionWays.ts) (43 ways pour la couche documentaire, plus les six ways du prolongement vers Sandaga ; versions, suites de nœuds et coordonnées WGS84) et [`busSectionReview.ts`](../../src/data/busSectionReview.ts) (repères versionnés, affectations, orientation et sources par portion). Les noms de présentation situent les nœuds, y compris les occurrences homonymes. Les textes des réseaux documentent la desserte, pas les coordonnées. Aucun tracé ni point des ZIP historiques ou de Moovit n’est repris dans l’extrait.

## Contrôles reproductibles

1. Lire la relation ou les descriptifs indiqués, puis **les versions des objets membres** : par exemple [108821782 v15](https://api.openstreetmap.org/api/0.6/way/108821782/15.json), [quai 4666430953 v5](https://api.openstreetmap.org/api/0.6/node/4666430953/5.json), [branche d’entrée aux Maristes](https://api.openstreetmap.org/api/0.6/way/649705992/3.json). La version d’une relation fixe les IDs des membres, **pas** leurs géométries futures. `/full` courant n’est pas un instantané historique.
2. [`compileBusScope`](../../src/routing/busGeography.ts) exige une chaîne simple. La jointure entre ways requiert **même ID et mêmes coordonnées**. Sens unique, sommets intermédiaires et sauts (limite 300 m ; maximum observé 275,8 m) sont contrôlés. Les quais DDD sont projetés à ≤20 m avec un chaînage croissant. Les limites routières, y compris DDD, doivent être **des nœuds du way même**, dans l’ordre, sans projection. Aucune distance ne prouve à elle seule l’attribution d’une ligne.
3. `npx vitest run src/routing/busGeography.test.ts` : tous les couples orientés des 43 repères, pas de jonction entre portions. Exemple :

   ```sh
   npm run audit:place-connections -- --at 2026-11-18T19:00 \
     --from landmark:bus-osm-305375476 --to landmark:bus-osm-3403676386
   ```

   `DOCUMENTED_SECTION_ONLY`, AFTU 40, 938 m, pas d’horaire. Remplacer les IDs par les coordonnées : même un écart nul reste de la **proximité**. Le filtre sans marches exclut ces portions sans preuve d’accessibilité.
4. En CI, l’artefact `dakar-bus-occurrence-review` compare l’inventaire (toutes provenances) et les membres du PBF téléchargé : rangs répétés, rôles, versions, sens des chaussées et sommets. Les objets de station épinglés comprennent les **paires dans les routes B1** et les membres **non appariés** des deux zones d’arrêt. Un changement de rang/objet appelle une revue, **jamais une activation**. Les ordres et coordonnées des pièces non attribuées ne sont pas importés.
